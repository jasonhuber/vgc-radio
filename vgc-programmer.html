APRS / BSS settings

What do APRS, BSS, KISS and TNC mean?

APRS (Automatic Packet Reporting System) is the open ham-radio standard for broadcasting your position and short text over the air — any APRS software, and sites like aprs.fi, can decode it. Using it requires a licensed callsign (N7WGP qualifies).

BSS is Vero Telecom's own packet protocol — same idea, no callsign check, but only other Benshi-family radios and the VGC app understand it. It's the fallback for anyone without a ham license.

The radio only ever transmits one of the two — set Format below to whichever fits.

TNC (Terminal Node Controller) is the packet modem — historically a separate box between a radio and a computer, translating between radio audio and digital bytes. This radio has one built in.

KISS is a dead-simple framing protocol so a computer can talk to a TNC without knowing anything radio-specific — it just gets raw packet bytes in and out. This app talks to the radio's TNC the same way, over the same Bluetooth link already used for everything else on this page (not a separate Bluetooth connection). The experimental terminal below sends raw payload bytes; receiving shows up in the Protocol log page as packet in…, and — if the coverage log is running — as a row there too, with your position attached. The full APRS / packet walkthrough is in the instructions →

Callsign / SSID — your callsign identifies the station; the SSID (0–15) is a suffix (like the -9 in N7WGP-9) used when one callsign runs several devices at once, so they don't collide on the map.

Symbol — the two-character code that picks the icon APRS software draws for you (a car, a house, an HT, …). Leave it as whatever the radio ships with if unsure.

Share location — turns GPS beaconing on/off and how often (in seconds) a position report goes out.

PTT-release options — what gets sent automatically the instant you let go of the transmit button: your position, your ID text, and/or your BSS ID.

Still set elsewhere: which RF channel carries packet data (part of general radio settings, a separate not-yet-built page — see PLAN.md). Set it from the radio's own screen or the VGC phone app for now: Menu → General Settings → Digital Mode → Digital Channel.

Connecting the radio

Do these in order. The second and fourth steps are the ones people skip, and both produce a failure that looks like the radio simply isn't there.

  1. Quit the VGC phone app and turn Bluetooth off on the phone. The radio serves one controller at a time, and a phone that has paired before will silently grab it back.
  2. Put the radio into Bluetooth pairing mode from its own menu.
  3. Press Connect radio (top right of any page here) and pick VR-N76 from the browser's device picker.
  4. Accept the operating system's pairing dialog. This is not optional: the radio accepts an unbonded link and then drops it about a second later, which looks exactly like a failed connection. The browser hands bonding to the OS, so the OS prompt is the browser's pairing prompt. Once only.

If the picker comes up empty, use Show all Bluetooth devices on the Radio link page. BLE advertising names often differ from the name the operating system displays.

The link is retried five times automatically, because this radio has a habit of dropping the first attempt right after service discovery starts. Watch the Protocol log page if you want to see it happen.

Programming channels onto the radio

The flow is: pick channels → arrange them into groups and slots → write. Nothing is sent to the radio until you press a write button, and every write asks for confirmation first.

  1. Read what's already there first. Read radio → compare pulls every slot off the radio and fills the On radio column, so you can see what's already correct. Skipping this is how people overwrite a channel they wanted.
  2. Narrow the library. Use the category chips (Simplex, Phoenix Metro, Rim Country, GMRS/FRS, Satellite), or go to the Map page and click a site to show only that site's channels — the filter follows you back to the Channels page.
  3. Or let it lay itself out. Auto-arrange all groups plans the whole radio in one press. By category gives each library category its own group, spilling a big category across consecutive groups; nearest first orders everything by distance from the QTH; by band splits 2 m from 70 cm. It shows you the proposed layout and asks before replacing the plan, and it never touches the radio.
  4. Then rearrange by hand. Leave show every group ticked and all six groups sit side by side. Drag any slot onto any other — same group or a different one — and the two swap, so nothing is ever lost by dropping in the wrong place. Drag a row from the channel library straight into a slot. Close gaps and Sort by frequency tidy the selected group.
  5. The older way still works: pick the target group, then either press Fill empty slots from shown list to drop the whole filtered list in, or click a slot to target it and press + on a specific channel.
  6. Write. Write this group → radio for one group, Write every group → radio for all of them. Both re-read afterwards so the On radio column reflects what's actually stored, not what you hoped.

Bringing your own list: Import CSV takes a CHIRP-format CSV, which is what most repeater directories and other programming software export. Export CSV writes the same format back out. Reset to built-in throws your edits away and reloads the list this page shipped with.

Groups and slots — what the numbers mean

The radio stores channels in groups (the manual calls them regions or zones) of slots. A VR-N76 is specified at 6 groups of 32, so 192 channels. The radio reports its slots-per-group correctly over Bluetooth but lies about its group count, which is why both numbers are editable on the Channels page — set them to match your radio.

The library's own Category (Simplex, Phoenix Metro, …) is just a filing label here. It is not the radio's group. The mapping between the two is deliberately explicit: one library channel can sit in as many groups and slots as you want.

Every group and channel number shown here is 1-based, matching what the radio's own screen displays. The protocol underneath is 0-based; the translation happens at the edge so you never have to think about it.

Group switching is the one thing still not confirmed on hardware. The command that selects a group returns nothing at all — no acknowledgement, no error — so a wrong value and a working one look identical from here. Probe groups reads channel 1 out of each group and tells you whether they differ. If every group comes back identical, group switching isn't working and you should program one group at a time, switching groups on the radio itself.

The coverage log

This answers one question: from where can I actually hit which machine? It records a row every time the radio's squelch opens — the channel, the peak signal, how long it lasted, and your position at that moment from the phone's GPS.

How to run it

  1. Connect the radio.
  2. Optionally Read radio → compare first. The log labels each hit with the channel's name and frequency, and it can only do that for slots it has read.
  3. Start scanning on the radio, or just park on one channel. Which channels get scanned is the per-channel Scan flag in the channel editor — set it to Skip on the ones you don't want swept.
  4. Press Start a session and grant the location permission when the browser asks.
  5. Leave this tab in the foreground with the screen on, and drive.
  6. Press End session when you're done — or don't, and it will end itself.

Sessions

Each run is a session: one drive, one hilltop, one evening. Pick an old one from the dropdown and the map, the totals and both tables switch to just that run, so you can compare the drive up the Beeline against the drive to Tucson. Rename… gives a session a name you will recognise in six months.

Sessions end themselves. People forget — especially the person who just parked and walked into a building. If nothing is heard for the number of minutes set next to the start button (10 by default), the session closes on its own and the strip counts down to it while you watch. A session that recorded nothing at all is discarded rather than cluttering the list.

The bubble map

This is its own map, not the repeater map, and it fits itself to whatever session you are looking at — including one four hours down the road. Every reception is a bubble at the place you heard it from, sized and coloured by signal strength, so a strong machine is a big green circle and a scratchy one is a small red dot. Hover any bubble for the channel, frequency, exact strength, duration and time.

Underneath the bubbles is your breadcrumb track — a point every 25 m or so of movement. This is the half people forget to record: the track shows where you drove and heard nothing, which is what turns a pile of hits into an actual coverage map. Toggle it, and the faint repeater-site rings, above the map. There is a scale bar bottom-left.

The tab has to stay in the foreground. A backgrounded mobile browser suspends Bluetooth notifications and throttles GPS, and you will silently log nothing. The page asks the browser for a screen wake lock when logging starts, but that only keeps the display awake — it does not survive switching apps. Phone in a mount, screen on, this tab in front.

What comes out

By channel summarises what you heard and how far from the QTH you were when you heard it. Every reception is the raw list. Export CSV is for a spreadsheet; Export GeoJSON drops straight into any mapping tool that reads it. Both include latitude, longitude and GPS accuracy per row unless a privacy zone redacted them. Ticking plot on the map draws the points onto the repeater map below, coloured by signal strength.

The local log is capped at 5000 receptions and 8000 breadcrumbs and also syncs to your account. It survives a reload; the synced copy survives clearing site data. Export before a long trip's data matters to you. Exports cover whatever the session dropdown is showing — the GeoJSON carries the receptions as points and each session's track as a LineString.

What it can't do — read this before trusting the numbers

  • It cannot start the scan. There is no known command to start or stop scanning on these radios — the protocol has never been reverse-engineered that far. The scan flag per channel is settable from here; pressing scan is not. Start it on the radio.
  • It logs that a signal was there, never what was said. Receive audio runs over Bluetooth Classic, which browsers cannot open at all. There is no way around this from a web page.
  • Signal strength is four bits. Sixteen steps, uncalibrated, shown here as a percentage because that is honestly all it is. Good for comparing one spot to another; not a dBm reading, and not something to quote.
  • Group and signal strength need the extended status format. Some firmware sends a short status message with neither. If the group column reads 1 everywhere and the signal column is empty, that's what happened — the rest of the row is still good.
  • Timing is coarse. The radio is polled every second or so while logging, plus whatever it pushes on its own. A transmission shorter than about a second may be missed, and durations are approximate. Sub-half-second squelch flutter is discarded on purpose.
  • Position is the phone's, not the radio's. Which is the better of the two, but it does mean a phone with no GPS fix logs rows with no position — the row still records the reception, just without a location.

APRS, BSS, TNC and KISS

What APRS is for

APRS — Automatic Packet Reporting System — is a shared, one-to-many data channel riding on top of ordinary FM voice radio. Instead of talking, the radio sends a short burst of data every so often, and every other station in earshot hears it. The four things people actually use it for:

  • Position reporting. The radio takes its own GPS fix and broadcasts who and where. This is the one that puts a moving icon on a map — useful on a drive, a hike, a bike ride, a public-service event, or so somebody at home can see you are moving.
  • Short text. A fixed status or beacon message rides along with the position, and full APRS supports point-to-point messages between callsigns.
  • Local awareness. Because everyone hears everyone, a receiving station builds a live list of who is nearby and how far away — before anybody says a word.
  • Infrastructure and telemetry. Weather stations, repeater bulletins, event traffic.
APRS is public, and it is archived. Anything this radio beacons is heard by anyone in range, forwarded onto the internet, and kept by sites like aprs.fi essentially forever — including a searchable history of every position, by callsign. That is the point of the system, not a flaw, but decide deliberately before turning on periodic beaconing from a house, a school, or a child's radio. Beaconing off, receive on, is a completely normal way to run APRS.

How a beacon actually gets from this radio to a map

Worth understanding, because when APRS "doesn't work" the failure is almost always one specific link in this chain:

  1. The radio's TNC builds a packet — your callsign, SSID, symbol, GPS position and beacon message — and keys the transmitter for about half a second of noise. That is a normal FM transmission on a normal channel; nothing special about the RF.
  2. It goes out on the APRS channel. In North America that is 144.390 MHz simplex, and everyone shares it. This must be the radio's digital channel — see set on the radio itself below. Wrong frequency is failure number one.
  3. A digipeater hears it and repeats it, if your path asks for that. Digipeaters sit on hilltops and give a 5 W handheld the range it would never have on its own.
  4. An iGate hears it and forwards it to the internet — into APRS-IS, the global backbone every APRS website reads from.
  5. aprs.fi (and friends) draw it on a map. Look yourself up at aprs.fi by callsign-SSID.

Steps 3 and 4 are other people's equipment. In the Phoenix metro area coverage is good; in the Rim Country it is patchy, and a beacon that nothing hears simply vanishes with no error anywhere. Silence on aprs.fi does not by itself mean the radio is misconfigured.

The four words

APRS is the open ham standard described above. Anything that speaks APRS can decode it. It requires a licensed callsign, and the licensee is responsible for what the radio sends.

BSS is Vero Telecom's own packet format. Same idea, no callsign required, but only other Benshi-family radios and the VGC phone app understand it — nothing on the ham APRS network will see it, and it never reaches aprs.fi. It is the option for someone without a licence, or for a private group of these radios talking among themselves. The radio transmits one format or the other, never both — that's the Format selector on the APRS page.

TNC — Terminal Node Controller — is the packet modem: the thing that turns bytes into tones a radio can transmit, and tones back into bytes. Historically a separate box wired between a radio and a computer. This radio has one built in, which is the whole reason it can do APRS with no extra hardware.

KISS ("keep it simple, stupid") is the minimal framing protocol a computer uses to hand raw packet bytes to a TNC and get them back, without either end needing to know anything about the other. It's the lingua franca between packet software and modems.

There is no separate connection to make. The radio's TNC is reached over the same Bluetooth link this page already uses for everything else — the same GATT service, the same commands. You do not pair a second time, and there is no serial port or KISS TCP socket involved.

Setting APRS up

  1. Connect the radio, then open the APRS & packet page.
  2. Press Read from radio first, always. A write sends back every field including ones this page doesn't show, so it must start from the radio's real values.
  3. Set your callsign and SSID (see the table below). Six characters maximum — that is the protocol's limit, not this page's.
  4. Pick a symbol, the two characters that choose the icon APRS maps draw for you. /[ is a person on foot, /> a car, /- a house, /b a bicycle, /k a truck. The first character is the symbol table (/ is the normal one); the second picks the icon.
  5. Set Format to APRS (licensed) or BSS (no licence).
  6. Write a beacon message if you want one — 18 characters that ride along with the position. A name, a purpose, a monitored frequency. It is public; keep it that way.
  7. Share location plus an interval turns on periodic beaconing. See the interval guidance below. Leave it off if you only want to receive.
  8. The PTT-release toggles decide what goes out automatically the instant you let go of the transmit button — position, ID text, BSS ID, or nothing. Handy on a voice channel; pointless if the digital channel isn't the one you're talking on.
  9. Set the digipeater path — see below — and press Write path. It is a separate command from the settings write, with its own confirmation.
  10. Press Write to radio, then Read from radio again to confirm it took.
  11. On the radio itself, set the digital channel to 144.390 MHz: Menu → General Settings → Digital Mode → Digital Channel. Nothing transmits usefully until this is right.
  12. Make sure the radio's GPS is on and has a fix. No fix, no position beacon.

The digipeater path

The path is your request for how many times other stations should repeat your packet. It is written as a comma-separated list, and for almost everybody the answer is:

WIDE1-1,WIDE2-1

That means "one hop through a local fill-in digipeater, then one hop through a wide-area one" — two hops total, which is the accepted norm for a handheld or a vehicle in populated country. WIDE2-1 alone is the polite choice if you are already high up or close to a hilltop digipeater. An empty path is direct-only: nothing repeats you, which is fine for testing whether a nearby iGate hears you at all.

More hops is not better. Every extra hop multiplies your packet across the whole region on a channel everyone shares, and the network's convention is two hops maximum. WIDE3-3 and friends are considered abuse and some digipeaters will simply drop them.

The path field takes up to 40 bytes. This page writes it and immediately reads it back, so the value shown after a write is what the radio actually stored.

Choosing an SSID

The SSID is the -7 in N7WGP-7: a number 0–15 that lets one callsign run several stations without them colliding on the map. It has no legal meaning — the callsign is the identification — but the conventions are near-universal and worth following:

-0 (none)Primary / home station
-5Phone or tablet running APRS software
-7Handheld radio — what this radio usually is
-9Vehicle / mobile
-10Internet gateway (iGate)

Two radios in the family

Each licensed operator beacons under their own callsign. An APRS position report is a station identification, so a second radio must not go out under someone else's call — even a parent's, even with a different SSID. Give each radio its own callsign, and use the SSID to separate that person's own devices (handheld -7, car -9).

Two radios that beacon under the same callsign and the same SSID will fight for the same icon on the map: aprs.fi will show one station teleporting between two places. If that is what you're seeing, it's duplicate SSIDs, not a broken radio.

Programming a second radio is otherwise the ordinary flow — connect it, Read radio → compare, write your groups. The channel library and layout on this page are stored in the browser, not the radio, so the same plan can be written to as many radios as you like. Only the APRS page's callsign, SSID and symbol need to differ per radio, and those live on the radio, so remember to Read from radio after connecting a different one — otherwise you are looking at the previous radio's values.

How often to beacon

The interval field is in seconds and the radio stores it in steps of ten. The channel is shared by everyone within a hundred miles, so this is a courtesy setting more than a technical one:

Fixed / at home600–1800 s. A station that isn't moving has nothing new to say.
Walking, hiking300–600 s.
Driving60–180 s.
Faster than 60 sOnly for a short, specific reason — a race, a search. Not all day.

The rest of the fields

Send power/voltage appends the radio's battery voltage to what it sends. Allow position check lets another station poll you for a position instead of waiting for your next beacon. Max forward hops and time to live control forwarding in BSS mesh mode — their meaning is taken from the field names in the reference implementation and has not been verified on hardware, so leave them at whatever the radio shipped with unless you are experimenting with BSS specifically. They are not the APRS path.

Proving it worked

  1. Watch the radio: at the interval you set, it should key up briefly on its own. If it never transmits, the usual causes are share-location off, no GPS fix, or the digital channel not set.
  2. Open aprs.fi and search your callsign-SSID. A position within a few minutes means the whole chain works.
  3. Nothing on aprs.fi but the radio is transmitting? You are probably out of range of an iGate, or the path is empty. Try WIDE1-1,WIDE2-1, and try again from a higher or more open spot before changing anything else.
  4. The radio's own screen showing other stations' packets is proof the frequency is right — if you can hear the network, the network can probably hear you.

Receiving packets

Already works, with no setup beyond being on the right channel. The radio pushes every packet it decodes, and they appear on the Protocol log page as packet in… frag N: … with the printable bytes shown. If the coverage log is running, each packet also becomes a row in it with your position attached.

What you'll see is the raw frame, not a parsed message — AX.25 and APRS decoding on top of it isn't built yet. You can usually read callsigns straight out of the ASCII.

Transmitting packets — experimental

The terminal sends raw payload bytes with HT_SEND_DATA, fragments them, and waits for each radio acknowledgement before sending the next. It does not build AX.25 or APRS packets yet: text mode is useful for compatible experiments; hex mode expects an already-built frame. The page blocks a send while the radio reports TX, RX or open squelch and requires typing TRANSMIT. Licensing, identification and channel selection remain the operator's job.

Ordinary APRS beaconing does not go through this terminal. Beacons are generated by the radio itself from the settings above — the terminal is for hand-built packet experiments.

The rules, briefly

  • APRS transmit requires an amateur licence, and the packet carries the callsign of the station responsible for it. BSS format is the no-licence path, and it stays inside the Benshi family.
  • The callsign you beacon must be the one you are licensed under. Do not share a callsign between operators.
  • No encryption, no obscured meaning, and nothing commercial — this is a public channel in every sense.
  • Automatic beaconing still identifies you: an unattended radio quietly beaconing your home position all day is legal but tells everyone where you live.

What still has to be set on the radio itself

One setting still matters for packet and is not reachable from this page yet:

  • Which RF channel carries packet data — Menu → General Settings → Digital Mode → Digital Channel. In North America APRS lives on 144.390 MHz. Part of the general radio settings page, which isn't built.

Also on the radio, not here: volume, squelch level, mic gain, dual watch, and the scan start/stop button itself.

Troubleshooting

The device picker is empty

The radio isn't in pairing mode, or a phone has already claimed it. Turn the phone's Bluetooth off. Then try Show all Bluetooth devices — the advertised BLE name is often not the name you see in system settings.

It connects and immediately disconnects

Almost always an unaccepted pairing prompt. The radio drops any link that isn't bonded. Look for a system pairing dialog — on Android it can appear as a notification rather than a dialog. If you previously paired and then removed the radio, remove it from the operating system's Bluetooth list as well and pair fresh.

"No Bluetooth adapter"

On macOS: System Settings → Privacy & Security → Bluetooth, enable your browser, then restart the browser. On Brave, Web Bluetooth is behind a flag at brave://flags/#brave-web-bluetooth-api.

Writes fail with an error status

Writing past the radio's real capacity returns INVALID_PARAMETER for each slot. Check the slots-per-group number matches your radio. The Protocol log page shows the radio's actual reply status for every failed command.

The live status strip is empty or missing fields

Some firmware sends the short status format without signal strength or current group. It is not an error and nothing else is affected.

Limits, and the honest disclaimers

  • No audio, ever. Bluetooth audio and Bluetooth PTT are Classic profiles; browsers only get BLE. The phone app has them because a native app can open Classic. Everything except audio is reachable from here.
  • This protocol was reverse-engineered, not documented. The mapping comes from benlink by Kyle Husmann, with the group-name and region details from HTCommander. Some of it is confirmed against real hardware and some is inference. Where this page is unsure, it says so on the panel itself.
  • Read before you write. Every panel that writes says this, and it is not boilerplate — a write sends back whole records, including fields no UI here displays.
  • Site positions on the map are approximate — named peaks and city centroids, not surveyed antenna locations. Distances are good to a mile or so, which is the right precision for deciding what to program.
  • Transmit only where you're licensed, on frequencies you're authorised to use, at power levels you're allowed. The GMRS and satellite entries in the library in particular have their own rules. Writing bad values to a radio is your responsibility.
